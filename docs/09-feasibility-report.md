# 个人网站实施可行性分析报告

评估日期：2026-10-07（Asia/Shanghai）  
评估对象：当前工作区中的规范、架构与接口文档、HTML 设计稿、设计截图及 M0 工程骨架。  
评估方式：资料交叉核对、代码检查、生产构建、HTTP 冒烟、设计稿静态检查、依赖审计、官方资料核实。此次仅新增报告，未修改业务代码、执行数据库迁移或升级依赖。

## 1. 结论

**项目技术上可行，现有工程可以继续使用；当前应先统一实施规范，再进入业务开发。现有资料足以支撑页面和主要业务的实现，但还不能直接作为无歧义的完整验收合同。**

它实际是“个人品牌网站 + 小型内容管理系统 + 配置驱动展示系统”，工作量主要来自后台、编辑器、媒体、权限和缓存一致性，而非五个前台栏目本身。

| 维度 | 判断 | 依据 |
|---|---|---|
| 产品与功能 | 可行 | 五大内容模块定位明确，主要字段、交互和边界已有设计 |
| 架构 | 可行，需要补齐关键机制 | 单体全栈、RSC 读服务层、后台 REST 写入适合此规模；动态路由和缓存契约尚不完整 |
| 数据模型 | 大部分可复用 | 实际 Schema 与数据文档均有 14 个模型；Schema 校验通过，但部分接口超出字段能力 |
| 视觉实现 | 可行 | 有共用 CSS、33 个源稿和 45 张截图；三端和暗色覆盖仍需补全 |
| 当前工程 | 可继续开发 | 类型检查、lint、静态校验和生产构建通过；业务功能尚未接入 |
| 生产部署 | 有条件可行 | 上传、分布式限流、备份和数据库连接需要按实际平台调整 |
| 原排期 | 偏乐观 | 部分阶段明细与总数不一致；鉴权、编辑器和可配置动效存在额外验证成本 |

**推荐决策：保留总体架构和已有设计资产，先完成“文章发布 → 前台阅读 → 模块关闭 → 恢复”的纵向闭环，再扩展其余模块。** 不建议从头重建工程，也不建议先做全部页面外观，再补数据与权限。

## 4. 开工前应处理的核心问题

### 4.1 新旧动效合同不兼容（P0：规范阻断）

《设计规范》与 08 的新版章节采用 `static/editorial/narrative/kinetic` 编排预设及独立装饰预设，默认 editorial + 无装饰。新设计稿也已采用两级结构。

但 08 §3 的完整结构与 Zod 仍采用旧 `minimal/breath/aurora/...` 枚举，03 §5.8、04 §15、07 M4.5 和实际 seed 也保留旧方案。具体冲突包括：

- 新预设 `editorial` 不在旧 Zod 的 `preset` 枚举中。
- 新的 `heroType='mask-lines'`、`easing='outExpo'` 不被旧枚举接受。
- 新 `sectionType`、`layout.flip` 等字段在旧结构中缺失，可能被默认 Zod object 解析丢弃。
- 新预算 28KB / 首屏 135KB，与旧验收 25KB / 110KB、默认 breath 为 0KB 不一致。
- 一处称删除粒子，一处保留粒子；一处称后台不加载 Anime.js，一处又要求后台真实动效预览/排序使用该库。
- “全部动效写在 motion.css、组件不写动画代码”的约定，与 Anime.js 接入示例直接冲突。

**建议：**在实现前产出一份最终配置类型、完整默认值、Zod、API 示例和预设清单，同步 seed 与验收。已有 `version:1` 的旧配置应有明确转换规则，不能只改枚举名字。区分“后台普通页面不加载动效库”和“动效预览页按需加载”；CSS 动画集中在 CSS，JS 编排集中在运行时模块。

### 4.2 上传限制与推荐部署平台冲突（P0：部署阻断）

03 §5.5 要求图片 10MB、视频 50MB、文档 20MB，经 multipart Route Handler 上传；推荐平台 Vercel 的 Function 请求/响应体上限为 4.5MB。按原方案实现，允许范围内的文件仍可能在到达业务校验前被平台拒绝。[Vercel 官方限制](https://vercel.com/docs/functions/limitations)

**建议：**生产采用“后台申请上传授权 → 浏览器直传对象存储 → 服务端确认并登记”的链路。文件先进入未公开的临时区，服务端确认真实类型、大小、归属和处理结果后再公开；不能因为改成直传就省略原有校验。缩略图/格式转换另行规划执行位置。LocalDriver 保留给本地开发，生产不依赖写入应用的 public 目录。[Vercel 文件使用指南](https://vercel.com/kb/guide/how-can-i-use-files-in-serverless-functions)

### 4.3 “后台可改路由”缺少运行时映射（P1：架构高风险）

01/03/04 要求将 `/logs` 改为 `/notes`，旧链接自动 301。但 Next.js 的文件路由不会因更新 `Module.route` 自动改名，当前注册表也只是保存字符串。

**建议：**实现前明确选择：首版固定栏目路径，或完整实现 catch-all/内部 rewrite 分发和运行时别名。若保留改路由，需要覆盖列表、详情、分页、分类/标签、metadata、sitemap、RSS、站内搜索链接及旧地址重定向。

数据库 `Module.route` 目前没有唯一约束，仅服务端“先查重”存在并发冲突窗口。校验还应覆盖保留路径的子路径、模块间嵌套冲突、别名循环及 `/logs → /notes → /journal` 的多次更名链。首版固定路径是降低复杂度的建议，并非已获确认的需求变更。

### 4.4 “5 秒生效”缺少明确缓存边界（P1：核心验收风险）

文档将 tag 失效、ISR、CDN `s-maxage/stale-while-revalidate` 和浏览器已有页面视为同一条即时链路。实际应分别考虑 Data Cache、Full Route Cache、Router Cache、HTTP/CDN 缓存。

Next.js 15 官方说明：Route Handler 中的数据重验证不会立即清除浏览器 Router Cache。[Next.js 15 缓存文档](https://nextjs.org/docs/15/app/guides/caching)

**建议：**把“5 秒生效”限定为保存成功后发起的新请求，单独定义已打开页面是否需要主动刷新。模块、设置读取的所有页面必须关联对应 tag；timeline 变化还影响 about，Profile 变化还影响首页 Hero，分类/标签变化影响归档和关联文章。不能只失效本表 tag。

首版可对站点开关/配置公开接口采用 no-store 或独立的短缓存合同，避免再叠加一层难以失效的 CDN 缓存。验收必须包含“已预取页面、已缓存详情、搜索、RSS、sitemap、关于我经历”等入口。service 层也应区分缓存失效能力：离线脚本不能直接假设处于 Next 请求上下文。

### 4.5 模块 config 浅合并会丢嵌套字段（P1：数据正确性）

01 §7 与 03 §5.3 规定 `{...old,...new}`，但请求示例为 `{home:{enabled:false}}`。这样会整体覆盖原 `home`，丢失 limit/order；局部更新 types/sections 也有同样问题。

**建议：**为每个模块定义受约束的嵌套 patch；对象按已知字段合并，数组明确采用整体替换。合并后重新校验完整结构，再写库。未知键和危险对象键应拒绝，不直接使用任意对象递归合并。加入“关闭首页露出后排序/条数不变”的验证用例。

### 4.6 权限、会话与刷新存在合同缺口（P1：安全和体验）

- 01 权限矩阵允许 VIEWER 访问仪表盘/审计，但 middleware 示例仅允许 ADMIN/EDITOR，03 后台总览又写“需 EDITOR 及以上”。照抄会阻断 VIEWER。
- Access Token 示例没有 session id；只撤销 Refresh Session 不能立即撤销未过期 AT。必须区分“停止刷新”和“立即停止本次会话的所有写操作”。
- AT 过期直接跳登录；RT Cookie 的 Path 限于 auth API。页面导航与客户端请求刷新需要有完整恢复流程，才能保留编辑草稿和 next 地址。
- 同一页面的 Promise 单例只解决单标签刷新；多标签仍可能同时轮转 RT，被误判重放。
- 文档首版使用内存 Map 限流，与推荐 Serverless 部署并不构成可靠的全局限流。

**建议：**统一权限表并在每个数据入口检查当前用户权限。会话是否立即可撤销需要确定实现，例如 AT 携带 sid、服务端检查会话有效性。刷新轮转应采用事务/原子条件并明确并发策略；生产限流使用共享存储或平台能力。写请求继续落实 Origin 校验，不能只依赖 httpOnly/SameSite。

### 4.7 接口清单和数据库字段不完全对应（P1：数据建模）

| 需求 | 当前缺口 | 建议 |
|---|---|---|
| 文章 reorder 写 `order` | Article 没有 order 字段 | 选择仅按置顶+发布时间，或补字段和排序合同 |
| 时间戳“同构全套 CRUD/回收站” | TimelineItem 没有 status/deletedAt | 单独定义 visible/showOnAbout 管理语义，或补软删除字段 |
| 定时发布 | 只有未来 publishedAt，没有已实现调度链路 | 所有公开查询过滤 `publishedAt <= now`，补定时失效任务及时间精度 |
| 草稿预览、slug 实时查重 | UI/模块文档有需求，API 缺完整合同 | 补鉴权、有效期、no-store、noindex，以及预览与查重接口 |
| 日期仅到年/月 | DateTime 无法保留输入精度 | 补 datePrecision 或收敛展示约定 |
| 拖动时间戳排序 | 说明混用“同年生效”和“同 startDate 生效” | 明确按日期优先还是人工顺序优先，UI 只允许有意义的排序 |
| 七个 About 区块独立开关 | sections 只有四个键 | 补 bio/services 开关或缩小“全部区块可关”的描述 |

ArticleUpdate 使用 CreateSchema.partial()，但接口宣称可选字段传 null 可清空；CreateSchema 中 summary/coverImage 等仅 optional，不接受 null。需要明确逐字段清空规则，不能直接照搬示例。

## 5. 实现与上线过程中应处理的问题

### 5.1 依赖安全与版本适配（P1/P2）

本次生产依赖审计报告 **30 个依赖条目，4 high、26 moderate**。主要关联链包含 Tiptap core/扩展、tiptap-markdown、Next 内嵌 PostCSS、Prisma config/deepmerge-ts。大量条目来自同一根因的传播，不等于 30 个独立漏洞，更不能据此认定现有占位网站已被利用。

上线前应按直接/传递依赖、开发/运行时、是否处理不可信输入分组，逐项升级或记录可复核的例外。部分修复建议跨主版本，不能使用 `npm audit fix --force` 作为统一处理方式。Tiptap 的升级尤其要结合 Markdown 兼容性验证。[Tiptap 官方仓库安全公告](https://github.com/advisories/GHSA-cp6q-959q-f8rh)、[PostCSS 安全公告](https://github.com/advisories/GHSA-6g55-p6wh-862q)

另有两项确定的版本适配问题：

- 实际 Prisma 6.19.3 客户端 `$use` 为 undefined、`$extends` 为 function；02 §2.4 的软删除 `$use` 示例不能直接执行。现有 prisma 单例 TODO 已写 `$extends`，应同步修正文档，并明确回收站、嵌套关系与批量操作的例外。
- Tailwind 为 4.3.3，tailwind-merge 为 2.6.1；应采用支持 Tailwind 4 的合并版本，避免后续 shadcn 类名合并出现不一致。[tailwind-merge 官方兼容说明](https://github.com/dcastil/tailwind-merge)

Anime.js、对象存储 SDK、文件类型检测、编辑器表格/图片等扩展和测试工具尚未作为完整实现依赖准备好。先按功能选择最小集合，避免一次性安装全部设想中的工具。

### 5.2 编辑器与媒体是实际难点（P1）

StarterKit 并不直接提供全部设计中的图片、表格、任务列表、自定义提示/折叠/视频块。还要保证这些内容在 Markdown 源码、Tiptap 和前台渲染之间往返不丢失。

建议早期用真实文章验证标题、嵌套列表、任务列表、表格、代码语言、图片 alt 和自定义块；定义语义等价标准，而非要求序列化后的每个空格完全相同。不支持的结构保留源码，不自动改写已有文章。自动保存应带版本条件，避免旧请求覆盖新内容；已发布文章的编辑暂存与重新发布语义也应明确。

媒体目前通过 URL/数组/Markdown 引用，没有独立引用表。“删除前扫描所有内容”小规模可行，但要覆盖 Profile/Setting、正文、图集和封面；内容导出 JSON 不等于媒体备份。导入需要定义 ID/slug 冲突、关系重映射、事务边界和失败回滚。外链 HEAD 检测如在服务端实现，还应限制协议、内部地址、重定向次数和超时，避免任意 URL 请求进入内网。

### 5.3 联系方式隐藏语义矛盾（P1/P2）

模块文档一方面要求 contactVisible=false 或关闭 About 后“联系方式彻底不可达”，另一方面又保留 social.email、mailto 社交链接以及首页/页脚联系方式。Profile 返回 null 无法隐藏其他出口。

应定义它是“只隐藏该区块”还是“全站隐藏邮箱电话”；若要求后者，必须在公共 DTO、首页、页脚、社交链接和结构化数据统一处理。邮箱用 JS 拼接只降低部分简单爬取，不能当作访问控制，也不应牺牲禁用 JS 时的核心可用性。

### 5.4 动效代码示例只能作意图参考（P2）

05 在子 layout 示例中再次返回 html/body，与当前根 layout 已拥有 html/body 冲突。应将站点动效配置放在前台作用域容器或设计合理的根布局策略。

现有 motion.css 背景创建在 `html::before`，scope=home 的关闭规则却选择 `body::before`，无法关闭同一个伪元素；当前没有注入这些属性，所以是接入后的潜在缺陷。`data-js-ready` 隐藏所有 reveal 的规则也应检查 off/disabled 场景，保证关闭动效仍可读。

08 的示例还对 Hero 子标题/CTA 使用 JS 时间轴，和“首屏 CSS”原则冲突；文档声称 CSS Hero 不影响 LCP，也需要真实性能验证，不能仅凭 0KB JS 作保证。API 类型、路由切换清理、用户偏好动态变化、设备能力缺失的 fallback 均应通过小范围原型确认。省电模式不是可跨浏览器可靠读取的统一开关，不应写成必然可测的强保证。

### 5.5 运维方案需要按平台落地（P1/P2）

Vercel Cron 触发 API 不代表函数中已经存在 pg_dump 工具、持久磁盘和完整备份执行环境。应选择数据库托管备份能力或独立任务环境，并备份媒体对象、设置和恢复所需关系。预览部署与生产数据库隔离；数据库应用连接与迁移连接按平台连接池要求配置。

目前只有开发用数据库 Compose，没有应用 Dockerfile、standalone 配置、反向代理和恢复脚本，因此 VPS 只是备选设计。还需落实 Cron/外部重验证鉴权、审计与过期 Session 清理、健康检查、错误追踪、日志脱敏和数据库恢复演练。

推荐托管组合的费用、可用额度和中国大陆访问体验应在部署前实测与核实；本报告不把文档中的“免费额度足够”当作成本承诺。

## 6. 设计稿落地可行性

视觉方向和常规布局均能用现有 Tailwind + React 组件实现，无需特别复杂的图形渲染。卡片、表格、抽屉和筛选具有明显复用空间。

但 HTML 稿应作为视觉与交互意图依据：检查到 33 个源稿均只有用于系统暗色判断的 script，没有业务事件处理；大量链接/按钮仅为展示。CSS hover/折叠能够运行，不代表保存、上传、筛选、拖拽和实时预览已经完成。

| 缺口 | 影响 | 处理方式 |
|---|---|---|
| 平板仅 2 张、暗色仅首页 | 容易遗漏后台/详情页中间布局和深色状态 | 优先补导航、编辑器、文章 TOC、媒体库和模块配置的边界状态 |
| 分类/标签归档、日志/作品独立编辑等没有全部独立稿 | 实现者需补交互细节 | 可复用已有模板，但需列出差异字段与验收项 |
| 移动首页作品：文档要求横滑，稿件是纵向四卡 | 布局验收依据冲突 | 开发前选定最终布局并同步两处 |
| 时间轴在 768px：规范写单列，IA 矩阵写中轴 | 平板布局冲突 | 以最终规范统一断点行为 |
| 首页导航：规范/seed 不显示首页项，设计稿显示首页 | 导航合同冲突 | 明确 Logo 回首页与首页 Tab 是否分别保留 |
| 页面中的封面/头像多为占位块 | 真实内容替换后密度、比例和 CLS 可能改变 | 准备真实封面、头像、简历和长短文本做验收 |
| 间距/圆角规范限制与 mock.css 有例外值 | 机械照抄无法同时满足规范 | 整理组件级例外，并建立共享 token 映射 |

**可访问性存在可计算的问题。**按规范颜色计算，小字 `#A1A1AA` 对白底约 2.56:1，暗色 `#71717A` 对 `#09090B` 约 4.12:1；白字对品牌 `#6366F1` 约 4.47:1，对危险色 `#EF4444` 约 3.76:1。这些组合如果用于普通文字，就低于项目自身的 4.5:1 要求。mock.css 中确有多处 11.5–12.5px 元信息使用 subtle 色。

应优先调整文本用途和语义 token，再处理逐组件状态。色值计算不是完整页面无障碍审计；禁用、装饰、大字等场景需要分别判断。设计 lint 全绿并未包含对比度、键盘焦点和屏幕阅读器验证。

## 7. 范围与排期建议

原路线总计 34.5 人天，其中 M0 为 2 天。但 M2 明细为 2.5+4+1.5+1=9 天，标题写 8 天；M3 明细约 12 天，标题写 10 天。再考虑用户/数据管理、定时发布、预览、安全修复、真实媒体和新动效合同，原排期不适合作为完整验收承诺。

以下为**单名熟练全栈开发者、按每人天 8 小时、已有设计获认可**的工程估算，属于规划判断，并非已测得工时。内容准备、域名办理、等待账号/外部服务不包含在编码人天中。

| 阶段 | 建议工作量 | 完成标志 |
|---|---:|---|
| 规范统一、依赖与数据库基础 | 2–3 人天 | 合同一致，依赖处置明确，迁移/seed 实际可跑 |
| 鉴权与后台入口 | 4–6 人天 | 权限、过期刷新、注销/撤销及并发场景通过 |
| 后台内容、编辑器与配置 | 10–14 人天 | 五模块管理闭环、真实上传、开关联动可用 |
| 前台及三端 | 8–11 人天 | 完整内容页面、主题、状态与导航可用 |
| 媒体完善、搜索与 SEO | 5–7 人天 | 媒体生命周期、全局搜索、RSS/sitemap/metadata 正确 |
| 新动效系统与配置预览 | 4–6 人天 | 最终预设可保存/预览，降级和实际预算通过 |
| 集成回归、部署和恢复演练 | 4–6 人天 | 生产关键流程、性能及恢复通过 |
| 基础合计 | 37–53 人天 | 不含缓冲 |
| 含约 20% 缓冲 | **约 45–65 人天** | 完整版较稳妥的预算 |

45–65 人天约 360–520 小时：全职约 9–13 周；若业余每周实际投入 20–25 小时，约 15–26 周。是否使用 AI 辅助、熟悉程度及最终范围会改变速度，应在第一条业务闭环完成后重新估算。

可发布 MVP 可考虑 **20–30 人天**：保留五大前台模块、基本内容管理、单管理员、安全登录、必要上传、模块显示/导航/首页配置、基础搜索和 SEO；暂缓动态改路由、完整导入恢复 UI、多角色用户管理、高级编辑器块、全部动效与复杂统计。这是供选择的范围方案，不意味着这些原需求已被取消。

## 8. 推荐执行顺序

1. **统一合同。**修正动效、嵌套 patch、权限、排序、隐藏语义、缓存生效边界及设计冲突；建立可追溯的验收清单。
2. **补足环境。**让当前机器有可用 PostgreSQL；可以恢复 Docker 路线，也可以使用兼容 PostgreSQL 环境。提交初始迁移并验证 seed；完成依赖影响评估和 CI 基础。
3. **完成第一条纵向闭环。**管理员登录 → 新建文章 → 图片上传 → 保存草稿 → 预览 → 发布 → 前台读取 → 修改 → 删除/恢复。先验证编辑器和媒体，避免复用一个尚未成立的模板。
4. **验证模块开关。**关闭文章后检查直链、列表、导航、首页、搜索、RSS、sitemap；恢复后验证数据与配置保留。若保留动态改路由，在此阶段完成对应原型。
5. **扩展其余四模块。**复用稳定组件，单独处理日志日期、作品图集、时间戳排序和 About 依赖，避免强行套同构 CRUD。
6. **补前台与上线能力。**做真实内容的三端/暗色验收、SEO、媒体引用、搜索以及备份恢复。
7. **最后接动效增强。**先 editorial + 无装饰，再验证 narrative/kinetic；以最终 Next 构建与真实设备测量替代独立库的体积估算。

首个里程碑宜限定为第 1–4 步的文章闭环与模块开关验收。它能提前暴露当前最主要的架构风险，并提供其余模块可复用的实现依据。

## 9. 上线门槛与最终判断

至少需要验证以下事项后再认定具备生产发布条件：

- 数据库迁移和 seed 可重跑，业务写入与审计一致；回收站/导入不覆盖现有有效数据。
- 服务端拒绝越权、草稿公开访问和已撤销会话写入；刷新并发不误踢用户；生产登录限流可靠。
- 模块开关、子类型过滤和联系方式隐藏在所有公开出口符合最终合同。
- 媒体支持真实允许尺寸，恶意/伪装类型被拒绝，引用中的对象不会被静默删除。
- 定时发布不会提前泄露，并按约定精度更新公开页面与订阅输出。
- 三端、暗色、键盘、禁用 JS/减弱动态效果下核心内容可访问；正文、长标题和代码不撑破布局。
- 使用统一口径测量 JS gzip、LCP/INP/CLS 和 Lighthouse；当前登录页 80KB 预算应结合已见约 103kB 共享基线重新确认。
- 依赖 high/critical 处置有结果，CSP 策略落实；本次 HTTP 未观察到 CSP 响应头。
- 生产环境隔离、健康检查、错误追踪、数据库及媒体备份具备实际证据，至少完成一次恢复演练。

**最终判断：可推进。**已有骨架和设计资料提供了可靠起点，主要问题可以通过合同统一和分阶段验证解决。当前最大的风险是把尚未统一的需求示例直接复制为实现，并沿用偏乐观的完整交付排期。先完成可验证的文章闭环和模块开关，再按实际速度扩展，是本项目最稳妥的实施方式。
