我为什么选择 Next.js

从渲染模型到工程化的一次梳理，以及我在真实项目里踩过的坑。

2025-01-15 · 8 分钟阅读 · 3200 字 · 1024 次阅读
封面 16:9 · 1200×675

起因

在过去的项目里，我一直在用不同的渲染方案。每次换技术栈的时候，我都会问自己同一个问题： 这次换，是因为它真的解决了我的问题，还是因为我想学点新东西？

这个问题不好回答。因为大部分时候，答案是"两者都有"。所以这篇文章试着把判断依据写清楚 —— 不是布道，只是把当时的思考过程留下来，方便三年后的我回看。

渲染模型

RSC 带来的最大变化不是性能，而是心智模型。你得先接受一件事： 组件可以永远不进入浏览器。

服务端组件

一开始我很不适应。写惯了 useState 的人，突然要面对一个没有状态、没有副作用、 没有事件处理的世界，会觉得手脚被绑住了。

但换个角度想：那些东西本来就不需要在服务端存在。你只是把边界画在了不同的地方。

app/articles/[slug]/page.tsx ⧉ 复制 
// 这个组件永远不会进入浏览器
export default async function ArticlePage({ params }) {
  const article = await articleService.getBySlug(params.slug)

  if (!article) notFound()

  return (
    <article>
      <h1>{article.title}</h1>
      <MarkdownRenderer content={article.content} />
    </article>
  )
}

注意这里没有 'use client'，也没有任何数据请求的 useEffect。 数据在服务端拿到，HTML 直接吐出去。首屏 JS 里不含这个组件。

增量静态再生成

文章发布后需要马上可见，但文章内容又极少变动 —— 这两个需求看起来矛盾。ISR 加上缓存标签解决了它：

发布文章时调 revalidateTag('article')，前台最长 5 秒生效。 既不是每次都查库，也不用等定时重建。

踩过的坑

有几件事是我在真实项目里才搞明白的：

  • middleware 跑在 Edge Runtime，不能用 Prisma。 我一开始把会话校验写在 middleware 里，构建直接报错。正确做法是 middleware 只验 JWT 签名， 真正的授权放在 service 层。
  • Server 和 Client 的边界比想象中更容易搞错。 一个不小心 'use client' 加在了 layout 上，整棵子树就都变成了客户端组件。
  • 缓存失效必须集中管理。 一开始 revalidateTag 散落在各个路由里，漏掉了两处，导致后台改了前台没更新。 后来统一挪到 service 层，问题就消失了。

关于取舍

没有银弹。Next.js 解决了我的问题（SEO、首屏、前后端一体），但也带来了新的复杂度（心智模型、缓存）。 如果你的项目是一个内部后台，我大概率不会推荐它。

结论

工具是手段，不是目的。我选它，是因为它让我一个人能维护一个完整的产品 —— 而不是因为它火。
