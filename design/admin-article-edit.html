渲染模型决定了你写代码的方式

我用 Next.js 不是因为它的生态大，而是因为它的渲染模型默认就站在了正确的一边。 RSC 把「数据获取」放回服务端，客户端只负责交互 —— 这件事看起来只是性能优化， 实际上它改变了组件该怎么拆、状态该放在哪、code 边界画在什么地方。

在一个日活三万的内容站里，我们把列表页从客户端请求改成了服务端直出， 首屏 LCP 从 3.2s 降到了 1.1s，同时删掉了 40% 的状态管理代码。 这不是框架的魔法，是它逼着你把「数据」和「交互」分开想。

不要问框架能给你什么，先问它强迫你放弃什么。愿意放弃的东西越多，架构就越干净。
app/articles/[slug]/page.tsx TypeScript · 24 行 
// 服务端组件：数据获取与渲染都在这一层完成
export const revalidate = 3600

export default async function ArticlePage({ params }: Props) {
  const article = await getArticle(params.slug)
  if (!article) notFound()

  return (
    <article className="prose">
      <h1>{article.title}</h1>
      <MDXRemote source={article.content} />
    </article>
  )
}

注意 revalidate —— 增量静态再生成让内容站在 CDN 上， 而作者改完文章不需要等任何构建流水线。
